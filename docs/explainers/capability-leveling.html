Capability Leveling

Run the cheap model first. Check its answer with something free. Escalate only when the check says you must — and the check is where all the interesting behaviour lives, because on our own workload the escalation never fired and the cheap retry did everything.

The shape of it shipped

This page is the reader-facing altitude. The design record behind it — control boundaries, invariants, falsification criteria and the evidence trail — is docs/plan-effort-leveling.md, and the configuration surface of the shipped part is docs/reference/workflow-leveling.md. Nothing on this page exists only here.

A workflow stage normally runs on one model and you take what you get. With leveling enabled, the stage runs on a weak or local model, its output is checked against a contract, and progressively more expensive repairs are attempted only as cheaper ones fail.

The order of those repairs is the whole design. Everything that decides is free; only the repairs cost anything.

stages:
  - agent_id: worker
    output_policy:
      output_schema: '{"type":"object","required":["records"]}'   # the check
    leveling:
      enabled: true
      max_escalations: 1          # rungs above the primary
      max_cost_usd: 0.50          # ceiling across the whole ladder
      ladder:
        - provider: anthropic      # resolved from the agent's own pool
      tier_policies:
        local: { retry_budget: 2 } # two free-model retries first

Model leveling: how the ladder knows what is above it shipped

Escalation only means something if the system knows which models are stronger than the one that just failed. Leveling keeps no capability benchmark for that. It reads two fields the model catalog already carries — per-token price, and whether the model is a reasoning model — and derives a tier.

Tier derivation — rules applied in this order
TierConditionEscalates?Default retries
unknownThe provider/model pair is not in the catalogNo — refuses to guess0
localPriced at zero in and zero out, i.e. self-hostedYes2
small-openPriced, not a reasoning model, output below the mid cutoffYes2
midA reasoning model below the frontier cutoff, or a non-reasoning model at or above the mid cutoffNot by default1
frontierA reasoning model at or above the frontier cutoffNo — nothing above it0

Cutoffs are $10 and $1.50 per million output tokens, both configurable per stage. Rule order matters more than it looks: a zero-cost model is local even when it advertises reasoning — a self-hosted DeepSeek-R1 is a local model, because the property leveling cares about is that retrying it is free. And an expensive non-reasoning model lands in mid, because frontier requires the reasoning flag; price alone does not buy the top tier.

What a rung actually is

A ladder rung is not another agent. It is a single chat call to a model the agent already has configured — one of its role models, or a named entry in its provider pool. Nothing is constructed and no routing layer is added. That keeps it cheap, and it costs something real:

  • No tools. A stage that depends on tool use cannot be rescued by escalation — the sharpest limitation in the feature.
  • No system prompt, no session, no memory. There is no conversation for a one-shot call to join.
  • The rung gets the original prompt, the failure reason, and the previous output. That is all it knows.

The winner's cost carries the whole ladder's spend — producing that output also paid for every retry and every losing rung. And max_cost_usd is checked between actions, never during one, so it can overshoot by a single call; the running total is a floor, because an attempt that ran a tool loop under-reports what it spent. It bounds runaway escalation. It is not a budget, and the code says so in those words.

Retry, errors, and loops shipped

Three different things here get called "looping", and they behave completely differently. Telling them apart is the difference between a retry that fixes 8 failures out of 8 and one that fixes 0 out of 18.

The payload is the point

A retry that just runs the model again is resampling, and resampling a weak model mostly returns a differently-worded version of the same mistake. What makes the retry rung work is what gets put back into the prompt:

# attempt 1 — the weak model writes a query
SELECT c.name, SUM(o.total_amount) FROM customers c JOIN orders o ...

# the check runs it. sqlite answers:
no such column: o.total_amount

# attempt 2 — that string is in the prompt now
SELECT c.name, SUM(oi.quantity * oi.unit_price) FROM customers c JOIN orders o ...
# executes. correct.

The database knows something the model does not, and the error message is the channel. All 8 execution failures resolved this way, which is where 57% → 77% came from. Compare the arm where a weak model was handed a semantic critique of its reasoning instead of a mechanical error: 0 of 18 repaired. Same loop shape, no outside information, no effect.

The loops, disambiguated
LoopScopeWhat comes inBounded by
Tool loopWithin a single attemptTool and query results — the outside worldmax_iterations, max_turns, max_tool_executions
RetryA fresh attempt inside one runThe failure reason from the checkmax_retries, or the tier's retry_budget
EscalationA fresh attempt on a different modelThe failure reason plus the previous outputmax_escalations, max_cost_usd

The loop can launder a visible failure into an invisible one

A check that sees only shape cannot see correctness, and repairing the shape can destroy a right answer. 2 of the 8 crashed SQL queries came back from retry as queries that ran and returned the wrong data. The crash was loud; the replacement is silent. In another trial the weak model produced the correct currency code in malformed JSON, and the retry produced valid JSON containing the wrong code — reported as success.

On an execution-only check, 83.3% was the structural accuracy ceiling: 7 wrong queries executed cleanly, drew zero escalations, and were invisible by construction. The strong model solved all 7 — the ladder never sent them, because nothing free could tell it to.

Raising that ceiling: let the database check the query designed, not built

"Does it execute" is a weak question. A database can be asked much better ones, and every one of them is answerable without reading a row of data — which means the ceiling above is not a law, it is a consequence of only asking the cheapest question.

The idea is a second ladder, made of checks rather than models, climbed in the same cheapest-first order. Each rung sees something the rung below it cannot.

Why EXPLAIN is the interesting rung

EXPLAIN binds every name and produces a plan without reading a row. That makes it strictly stronger than "does it execute" and strictly cheaper:

  • It is a correctness signal disguised as a performance tool. The 7 silent failures in the benchmark were wrong joins and invented arithmetic. A wrong join shows up in a plan as a product join or a scan nobody asked for — visible without running anything.
  • The optimizer reports its own confidence. A plan built on no-confidence estimates is a plan over columns the optimizer knows nothing useful about, which is often a sign the query is not asking what the author meant.
  • It is safe. No data is read and nothing is mutated, which matters because escalation rungs run without tools — a check that needs no tool call fits where a repair cannot.

DDL is the rung below it and the cheapest real check available: fabric.GetSchema already returns each field's name, type, nullability and primary-key flag. Comparing a generated query's column references against that catches invented columns and wrong join keys before the optimizer is even consulted.

DBQL is the rung above, and the only one that needs the phrase "where available". Today DBQL appears in Loom solely as domain knowledge inside Teradata performance patterns — things an agent can be told to query when analysing a system. Using it as a verification signal is different: it turns the query log into a baseline, so "this shape of query has never run on this system" or "the estimate is two orders of magnitude off the usual" becomes a flag. Backends already advertise what they can do through Capabilities.Features, which is where a check ladder would discover whether EXPLAIN and DBQL are reachable at all.

Why this is the highest-value thing not yet built

Every measured gain so far came from a free check plus a cheap retry. The measured ceiling came from the check being shallow. Deepening the check ladder attacks the ceiling directly, needs no new model, no new provider plumbing, and no change to the effort or model axes — and unlike the model ladder, it was never the part that failed to fire.

One honest caveat: a deeper check is still a check. Rungs 1–4 verify that a query is well-formed and plausible, not that it answers the question asked. Result verification is the only rung that sees meaning, and it costs a model call — which makes the top of this ladder a cost decision, not a capability one.

Two axes, one dial

There are two independent ways to spend more on a stage. Use a better model, or make the same model work harder. They are separate controls, they influence each other, and the measurements only mean anything because each was moved on its own.

Independent, but not unrelated

They move separately — you can raise effort without touching the model, and swap the model without touching effort. Three things nonetheless couple them, and all three are visible in the figure:

  • Capability. Not every model accepts a thinking budget. The dashed band marks where that band of the vertical axis simply does not exist — and notably, it is exactly the cheap end, where leveling matters most. Loop depth and retries have no such dead zone, which is why they are the dependable currency.
  • Cost. Moving right multiplies the price of every token; moving up multiplies the number of tokens. Whether high effort on a mid model beats one shot at a frontier model is arithmetic the catalog can do — and is unmeasured, because every arm we ran was priced at zero.
  • Substitution. A model that thinks longer may need fewer loops. Nobody knows by how much; that is the experiment, not the design.

The thinking level that is already named but not yet wired dead knob

Worth being precise about, because it looks finished: a thinking_level field already exists with the vocabulary none / low / medium / high, and six agent presets set it to high. The agent config loader never reads it. An agent created from a "deep thinking" preset gets no thinking, and nothing in the LLM provider interface can carry a thinking budget on a request anyway — temperature and max-tokens are fixed when the client is constructed.

That is good news in one narrow sense: the vocabulary is settled, so the effort axis should wire that name rather than invent a second one next to it. But it has to be wired or removed before it means anything. This project has form here — two per-tier knobs were deleted from the proto before merge rather than shipped as settings that controlled nothing.

The dial: an equalizer, not a volume knob proposed

The right model for the effort control is a graphic equalizer. An engineer gets the individual sliders. Everyone else gets a named preset that moves them together — and the preset is nothing more than a remembered position of those same sliders.

Names should describe the workload, not the sound — a reader picking a preset needs to know what it does to their bill and their error rate. Draft, Contract and Audit above are placeholders that at least say that much. The band layout also makes one thing pleasantly obvious: the leftmost slider is a different kind of thing from the other four. Moving it changes who answers; moving any of the others changes how hard the same model works.

What was measured

Five phases against live local models, plus a replay over the committed per-trial data. The SQL benchmark is closest to a real workload: 30 questions, generated SQL actually executed against SQLite, scored by result-set equality against reference queries.

Two interventions were measured and rejected rather than shipped. Self-critique repaired 0 of 18 wrong answers. Forcing step-by-step structure made a weak model monotonically worse — 27% then 3% against a 40% baseline — and its configuration knob was deleted before merge rather than left as a dead setting.

One caveat governs everything above: both models were local and priced at zero, so nothing here says anything about dollars, and the ladder has never actually escalated across a price tier.

Leveling makes a weak model's output meet a contract, and routes past the model when a free signal can see that it should. It does not make the model smarter.

The order that falls out of this is not the order of ambition. The check ladder comes first, because it is free, it needs no new plumbing, and it attacks the one ceiling that was actually measured. Loop depth comes next, because it works on every model including the ones that cannot think harder. In-model thinking comes last, because it is unavailable on exactly the models this feature exists to help — and because a knob that controls nothing is worse than no knob at all, which this codebase has already learned twice.
